# IfSave 개편 구현 계획 v0.1
_기준 문서: 개편 기획안 v0.2 (2026-09-30) · 대상: MVP(1단계) + 2단계 준비_

> **전제**
> 현재 IfSave는 모바일 웹 MVP로 배포되어 있고(ifsave.com), Gemini API·OCR·시장 데이터 연동·서버 계산 기반 숫자 검증이 동작한다.
> 이 문서는 **프레임워크에 독립적인 모듈·데이터·API 단위**로 쓴다. 현재 스택(프론트/백엔드/DB)을 확인해 주면 파일 경로와 마이그레이션 명령 수준으로 내린다.

---

## 0. 구현 원칙 5개

1. **판단 전 데이터와 판단 후 데이터를 물리적으로 분리한다.** 테이블·API·프롬프트 컨텍스트 모두에서 `pre`와 `post`를 구분한다. 프론트가 결과를 미리 받는 일이 없어야 한다.
2. **AI는 서버가 준 것만 말한다.** 기존 NumberGuard(숫자)를 QuoteGuard(인용문)·LeakFilter(사후 정보)로 확장한다.
3. **카드 1개 = 렌즈 3종.** 콘텐츠는 한 스키마로 저장하고 렌즈는 렌더링 옵션이다.
4. **모든 판단 이벤트는 연구 로그로 남는다.** 카드 버전·렌즈·근거·확신도·AI 대화 유무를 함께 저장한다.
5. **기존 화면은 지우지 않고 재배치한다.** 소비 기록·타임캡슐·페르소나·내 금융 기준은 새 모드의 부품이 된다.

## 2. 데이터 모델

### 2.1 판단 카드

```sql
-- 사례 메타 (판단 전 노출 가능한 값만)
cases (
  id            uuid pk,
  version       int,                 -- card_versions 참조
  sector_public text,                -- 공개 수준에 따라 '소프트웨어' 또는 '기술'
  size_bucket   text,                -- 소형/중형/대형
  horizon_days  int,                 -- 90~365
  difficulty    int,                 -- 1~5
  status        text,                -- draft/reviewed/live/retired
  data_cutoff   date,                -- 판단 시점 (마스킹, 서버만 보관)
  created_at, reviewed_at
);

-- 판단 전 블록. 렌즈별로 나눠 저장
case_blocks (
  case_id uuid fk, kind text check (kind in ('chart','fundamental','context')),
  payload jsonb                      -- 스키마는 §2.4
);

-- 판단 후 블록. 별도 테이블, 별도 권한
case_outcomes (
  case_id uuid pk fk,
  company_name text, ticker text, start_date date, end_date date,
  start_price numeric, end_price numeric,
  return_pct numeric, bench_return_pct numeric, sector_return_pct numeric,
  price_path jsonb                   -- [[date, price], ...]
);

-- 카드에 사전 지정한 학습 포인트
case_learning_points (case_id fk, concept_id fk, rank int);

concepts (
  id text pk,                        -- 'abs-vs-relative', 'growth-vs-valuation'
  title text, body_md text, quiz jsonb, lens_tags text[]
);
```

### 2.2 사용자 판단

```sql
judgments (
  id uuid pk, user_id fk, case_id fk, case_version int,
  lens text check (lens in ('chart','fundamental','both')),
  key_evidence text not null,        -- 근거 1개 필수
  extra_evidence text[],             -- 최대 3
  risk_factor text,
  direction text check (direction in ('outperform','underperform')),
  confidence int check (confidence between 1 and 5),
  invalidation text,                 -- Level 4
  ai_dialog_id uuid,                 -- 공개 전 대화 참조

judgment_outcomes (
  judgment_id pk fk, hit bool, relative_pp numeric, scored_at
);

concept_progress (
  user_id, concept_id, state text,   -- new/learning/review/known
  quiz_correct int, quiz_total int, last_seen
);
```

## 4. AI 오케스트레이터

### 4.1 역할별 컨텍스트 범위

| 역할 | 시점 | 컨텍스트에 넣는 것 | 절대 넣지 않는 것 |
|---|---|---|---|
| Questioner | 공개 전 | 렌즈 블록, 사용자 근거·확신도, 페르소나 말투 | outcome, 기업명, 날짜 |
| SealedParticipant | 카드 제작 시 | 판단 전 블록 전체 | outcome |
| Explainer | 공개 후 | 근거 문서 텍스트(retro), outcome, 사용자 판단 기록, 개념 | 문서 밖 추론 요구 |

### 4.2 Guard 체인

```
LLM 응답 → NumberGuard → QuoteGuard → LeakFilter → PersonaLayer → 클라이언트
```

- **NumberGuard(기존):** 응답 내 숫자를 서버 계산값 집합과 대조. 불일치 시 재생성 또는 해당 문장 삭제.
- **QuoteGuard(신규):** 따옴표·"~라고 밝혔다" 형태 문장은 `retro_evidence.text`와 부분 문자열 매칭. 불일치 시 삭제 + `🔍 추론` 라벨 강제.
- **LeakFilter(신규, 공개 전 전용):**
  1. 규칙: `data_cutoff` 이후 날짜 표현, 기업명·티커·제품명 사전, outcome 수치 탐지
  2. 판정 LLM: "이 문장이 판단 시점 이후 정보를 담는가?" 2차 판정
  3. 하나라도 걸리면 응답 폐기 → 안전 문장으로 대체("근거를 하나 더 말해줄래요?")
  4. 결과를 `research_events`에 기록 (누설 시도율 자체가 연구 데이터)

### 4.3 프롬프트 골격

```
[Questioner]
당신은 {persona} 말투의 질문자다. 정답을 모른다고 가정하고 절대 예측하지 않는다.
제공된 데이터만 언급한다. 사용자의 근거 '{key_evidence}'에 대해 반문 1개, 놓친 정보 질문 1개를 한다.
두 문장 이내. 숫자는 아래 목록의 값만 사용한다: {numbers}

[Explainer]
당신은 {persona} 말투의 해설자다. 아래 근거 문서와 결과만 사용한다.
사용자 가설 '{hypothesis}'와 문서의 논리를 비교한다. 문서에 없는 이유는 말하지 않는다.
결과를 하나의 원인으로 단정하지 않는다. 개념 {concept}를 한 문장으로 연결한다.
```

### 4.4 라벨 부착 규칙

- 응답을 문장 단위로 분리한다.
- 각 문장을 `source`(QuoteGuard 통과) / `inference`(모델 생성) / `uncertain`(판정 LLM 확신도 낮음)으로 태깅한다.
- 클라이언트는 문장 옆에 칩을 그린다. 카드 상단 배너는 `inference` 비율 ≥ 50%일 때만 표시한다.

## 5. 기존 어셋 재활용 맵

| 기존 어셋 | 상태 | 개편 후 역할 | 변경 범위 |
|---|---|---|---|
| 소비 기록 + 13종 자산 가상 매수 엔진 | 유지 | 소비 If 모드의 대안가치 계산 | 없음. 결과 화면에 개념 1개 연결만 추가 |
| 벤치마크 스위칭 (시장 국면 3단 판정) | 유지 | 소비 If 하락장 처리 / 판단 카드 벤치마크 선택 로직 재사용 | 국면 판정 함수를 공용 서비스로 분리 |
| 시장 데이터 연동 | 확장 | 카드 outcome·벤치마크 계산, 정규화 가격 경로 | 과거 구간 조회 함수 추가 |
| OCR (영수증) | 유지 | 소비 If 입력 | 없음 |
| Gemini API 호출 계층 | 확장 | Questioner·Explainer·SealedParticipant | 역할별 컨텍스트 빌더 3개 추가 |
| NumberGuard | 확장 | Guard 체인 1단계 | QuoteGuard·LeakFilter 뒤에 연결 |
| 페르소나 6종 (말투 레이어) | 유지 | 질문자·해설자 말투, 면책 문구 전달 | 프롬프트에 역할 분기 추가. 실존 인물 1인칭 금지 규칙 삽입 |
| 커스텀 페르소나 (내 기준 의인화) | 보류 | 3단계 복습 기능에서 검토 | MVP 미노출 |
| 타임캡슐 (봉인 → 개봉 → 채점) | 재사용 | ① 사용자 판단 기록 ② AI 가설 봉인 ③ 역추적 가설 봉인 | 봉인 객체 타입을 `judgment` / `ai_hypothesis`로 일반화 |
| 벤치마크 대비 채점 (실력/운 분류) | 재사용 | 결과 공개 화면의 상대 성과 계산 | 입력을 매매 기록 → 카드 outcome으로 확장 |
| 내 금융 기준 | 재사용 | 개념 숙련도 + 반복 오류 + 사용자 판단 원칙 저장 | 항목 타입에 `concept`, `rule` 추가 |
| 회고 화면 (매매 회고) | 재사용 | 결과 공개 화면 레이아웃 기반 | "판단 시점 근거 vs 결과 나란히" 구조 그대로 |
| 커뮤니티 배지 (기준 준수도) | 축소 | 2단계 가설 분포 공개 시 참여 지표 | 수익률·적중률 배지 없음 유지 |
| 금융행동 프로필 설문 | 유지 | 온보딩 → 렌즈 기본값 추천 | 문항 1개 추가(차트/재무 선호) |
| 데모 계정·시연 흐름 | 유지 | 카드 3장 시연 시나리오 추가 | |

**폐기 대상:** 없음. 실계좌 연동은 원래 없었고, 종목 추천 요소도 없었다.

## 6. 콘텐츠 파이프라인 (카드 제작)

```
scripts/
  fetch_prices.py      # 티커·기간 → 정규화 가격, 벤치마크, 업종 지수
  fetch_fundamentals.py# 판단 시점 이전 재무 4그룹 (미국: 공시일 기준 / 국내: DART 접수일 기준)
  build_case.py        # 블록 payload 조립 + 마스킹 적용 + 학습 포인트 지정
  check_case.py        # 체크리스트 자동 검사 → 실패 시 status=draft 유지
  seal_ai.py           # SealedParticipant 가설 생성 + LeakFilter 통과 시 저장
```

`check_case.py` 자동 검사 항목
- outcome 기간 이후 날짜가 pre 블록에 없음
- 기업명·티커·제품명 사전 매칭 0건
- 재무 수치의 공시일 ≤ data_cutoff
- 정정 공시(restatement) 미반영 확인 플래그
- events의 source·date 필수

수작업 항목: 업종 공개 수준 결정, 학습 포인트 지정, 검토자 승인(reviewed_at).

초기 목표: 판단 카드 12장(렌즈 3종 → 36개 판단 상황), 역추적 A등급 카드 3~5장.

## 7. 화면 구성 (MVP)

| 화면 | 핵심 요소 | 재사용 |
|---|---|---|
| 카드 | 진행 표시, 렌즈 세그먼트, 마스킹 메타, Core Card, More Info 접기 | 신규 |

| 결과 공개 | 기업·기간 공개, 기업 vs 벤치마크, 가격 경로, 내 판단 회고, 개념 카드, 퀴즈 | 매매 회고 레이아웃 |
| 개념 | 제목, 3문장 설명, 이번 사례 연결, 확인 문제 | 신규 |
