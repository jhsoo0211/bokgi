# 합치기 vs 새 앱 — 판단표

_체크포인트: **2026-12-12**(베타 9주차 뒤). 그때까지는 '별개 유지'가 기본값이다. 이 표는 기준과 사실만 적고, 가중은 체크포인트에 사용자가 매긴다._

## 1. 두 선택지

| | **A. 복기를 IfSave 안으로 합친다** | **B. 복기를 별개 앱으로 유지한다** |
|---|---|---|
| 모양 | IfSave의 한 모드(탭)로 들어간다. 소비 If와 판단 카드가 한 앱 | bokgi.ifsave.com(또는 새 도메인)의 독립 앱. IfSave와 로그인·데이터 분리 |
| 사용자에게 | "IfSave가 바뀌었다" | "새 서비스가 생겼다" |

## 2. 기준별 사실

| 기준 | A. 합치기 | B. 별개 |
|---|---|---|
| **브랜드·사용자 혼선** | IfSave는 소비·기회비용 앱으로 알려져 있고 공모전 PPT·운영 UI와 묶여 있다. 판단 카드가 들어가면 '무엇을 하는 앱인가'가 흔들린다 | 이름부터 학습 앱. 혼선 없음. 단, 서브도메인이면 IfSave 소속으로 보인다 |
| **운영 부담** | 스택 1개. 하지만 IfSave 백엔드(Java, 7만 줄)에 복기 도메인을 얹어 마이그레이션·권한·배포가 모두 운영 앱을 건드린다 | 스택 2개(IfSave 3컨테이너 + 복기 2컨테이너). 복기는 운영 앱과 완전히 분리돼 장애가 서로 번지지 않는다 |
| **개발 속도** | 기존 인증·시더·AI 체인을 그대로 쓴다. 대신 Java·Next 두 저장소를 오가고, 운영 앱의 CI·테스트(단위 2,891 + Postgres 33 + 프론트 1,149)를 매 변경마다 통과해야 한다 | Next 하나. 재사용 조각은 작아 하루 이식. 테스트는 복기 것만 |
| **공모전·연구 요구** | IfSave의 공모전 UI 일관성 제약을 받는다. 연구(LCHR)와의 연결을 설명해야 할 때 한 앱이 편하다 | 제약 없음. 연구와는 자산만 공유하고 연결을 주장하지 않는다(결정 D4) |
| **라이선스·규제 노출** | IfSave 운영 데이터(Twelve·Toss·KIS, 운영 키)와 섹션을 공유하면 복기의 표시 용도가 운영 키 라이선스에 얹힌다 | 복기의 자료원·라이선스를 따로 정한다(adr/0003). 규제 경계도 '교육 앱'으로 단순 |
| **데이터 공유 필요** | 소비 If(3단계)가 들어오면 소비 기록·기회비용 엔진을 바로 쓴다 | 소비 If를 하려면 엔진을 이식하거나 API로 잇는다(엔진은 순수 계산 클래스라 이식은 작다) |
| **수익·확장** | IfSave의 금융 교육 B2B 서사에 판단 카드가 붙는다 | 교실 모드(학습지)를 독립 상품으로 만들 수 있다. 앱스토어 출시도 독립 쪽이 단순 |

## 3. 전환 비용(결정이 바뀔 때 드는 것)

| 전환 | 드는 것 |
|---|---|
| B → A (나중에 합치기) | 복기 DB를 IfSave 사용자 계정에 연결(초대 코드 사용자 → IfSave 계정 매핑), 화면을 IfSave 디자인 토큰으로 재스킨, 도메인 리다이렉트, 운영 앱 배포 1회 |
| A → B (나중에 떼기) | 운영 DB에서 복기 테이블 분리, 인증 재구축, 사용자 재가입 요청. **더 비싸다** |

따라서 미정 상태에서는 B로 시작하는 것이 되돌리기 쉽다. B의 비용은 '스택 2개 운영'이며, 이는 beta 스택을 내리면서 상쇄된다.

## 4. 체크포인트에서 볼 것(2026-12-12)

1. 내가 9주 동안 매일 세션을 열었는가. 열지 않았다면 어느 쪽도 의미가 없다 → 복기 중단·축소를 먼저 검토.
2. 지인 10명 피드백에서 "IfSave와 무엇이 다른가"가 반복됐는가(→ 합치기 압력) / "소비 기록은 상관없다"가 반복됐는가(→ 별개 유지).
3. 공개 출시를 원하는가. 원하면 라이선스 비용과 도메인·브랜드 결정이 함께 따라온다.
4. 연구나 공모전이 한 앱을 요구하는 일정이 생겼는가.
